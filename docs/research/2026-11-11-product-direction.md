# Where Vibe Fence should go after the hackathon

Product research and recommendation · November 11, 2026 · Proposed direction, not a release announcement.

**Build a free companion that helps someone decide whether to keep, fix or share the change their coding tool just made.** The builder should be able to stay in the same chat, keep working without a checklist, and get a straight answer to two questions: *Did the thing I asked for actually work? Is there something here I should fix before I share it?* Vibe Fence already has part of the second answer. The first is the reason to return on an ordinary day when no security rule fires.

Start with two ways in: a short instruction someone can add once to a browser builder, and a local checker for people whose tool can work with a project folder. Same language and purpose; different abilities. Try [the companion card and pilot](2026-11-11-companion-pilot.md). Test both before choosing which audience to build for first.

## What a first-time user actually gets

I built the current working source in a temporary directory and tried the default install in a fresh Git project with one `package.json`, an empty user profile, no editor configuration and no provider credentials. I separately rebuilt and tried the local hackathon tag, without changing either checkout. The counts below are newly created regular files outside `.git`, including the ignored runtime, excluding the existing package file. They measure install scope, not how many files a user sees in the editor.

| Observation | Why it matters |
| --- | --- |
| The working 0.3.0 source added **101 files**, chose four editors, added three package scripts, and suggested checking Codex. The tagged 0.4.0 build added **102 files** and gave the same three next steps. Neither environment had an editor to detect. | The first message makes the beginner responsible for deciding which of four integrations is doing something. When the tool is unknown, offer a project-only check and one optional editor choice. |
| A harmless commit passed. A new staged reference to a private-key-shaped environment name exposed to the browser blocked the commit. After correction, Git accepted the change. No real secret or model request was involved. The same fix appeared three times in the block message. | Keep the automatic Git check. The staged scan passed; a second scan of the whole folder caused the block. | This is a real finding attached to the wrong decision. ## What the research changes

**People already try to check their work. Help them take the next step when the check fails.** In Fawzy, Tahir and Blincoe's survey of 162 vibe coders, manual testing was common across experience levels. Non-developers more often reported reprompting or abandoning debugging when they couldn't understand what went wrong. The group labels stopped predicting those behaviors once usage and independent coding experience were accounted for. A separate observed study of 21 introductory students found that 20 completed the exercise, yet completion masked substantial differences in understanding. These are a self-report study and a classroom study, respectively; neither establishes demand for Vibe Fence. They favor testing a concrete next action over adding another warning or tutorial. [Survey, §4.6](https://arxiv.org/abs/2605.24521) · [Prather et al., ICER](https://arxiv.org/abs/2405.17739).

**A passing build and a secure app are different claims.** A study of real vibe-coded apps found recurring placeholder behavior and exposed secrets; stronger prompting alone did not remove the risks. It does not establish how often our users encounter them or whether our scanner would catch them. A useful product response is specific: check whether a saved item survives a reload; separately inspect whether a supported kind of private key is being put in browser code. Report each outcome on its own. A successful compile establishes neither. [Deng, Fan and Meng](https://arxiv.org/abs/2606.23130).

**A small instruction can carry a habit; it cannot certify the output.** Gloaguen et al. found that extra repository context often increased cost without improving task success. Lulla et al., measuring a different outcome on 124 pull requests, found lower median runtime and output tokens with project instructions. Neither tested novices or proved that instructions enforce policy. Use the smallest text needed to ask for an observable result; test whether it helps compared with the host alone. [Context-file evaluation](https://arxiv.org/abs/2602.11988) · [Efficiency study](https://arxiv.org/abs/2601.20404).

**The browser audience needs its own test.** A CHI study combining an 85-person survey with interviews of 31 hackathon participants and eight practitioners found that cloud environments helped nontechnical users build prototypes. That makes a terminal-only launch a risky assumption. It does not tell us which host our audience uses most. Likewise, experiments on security warnings found that frequent, similar-looking routine notifications reduced attention to important warnings. Test quiet success and rare interruptions; do not assume a browser warning study predicts retention in a coding tool. [Prototyping study](https://doi.org/10.1145/3772318.3790757) · [Vance et al., SOUPS](https://www.usenix.org/conference/soups2019/presentation/vance).

**Your library supplies good test cases, not a vote for the old architecture.** One reader of the saved vibe-coding guide asks whether all the security checks must be done manually; another describes getting edits after asking a question. A recorded build in the Zed material illustrates an agent declaring completion despite placeholder behavior. Several of these documents were already read for the hackathon. The useful change is to turn those observations into tasks we can watch beginners perform. The [library notes](2026-11-11-library-notes.md) give the filenames, pages, evidence strength and selection limits.

## Where it fits among existing tools

| What is already available | What Vibe Fence should do differently |
| --- | --- |
| [Gitleaks](https://github.com/gitleaks/gitleaks) already scans for secrets locally. [GitHub push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection) blocks supported credentials on covered pushes. [CC Safety Net](https://github.com/kenryu42/cc-safety-net) already offers pre-action guards across many coding agents. These are documented capabilities, not head-to-head performance tests. | Do not compete on rule count or supported-editor logos. Test whether the builder can understand the consequence, repair the change and verify the repair **without leaving their normal workflow**. |
| [Lovable](https://docs.lovable.dev/features/security) has native security scans, and [Replit](https://docs.replit.com/replit-workspace/workspace-features/version-control) has checkpoints and rollback. | Use the native result when available and tell people exactly what it covers. If the native experience is already as easy and reliable, don't ship a second version for that host. |
| Repo instructions, project preferences, Git events and host hooks exist, but apply at different times and to different actions. [Git's hooks](https://git-scm.com/docs/githooks) act at specific Git events. | Say “checked before this commit,” “your assistant has guidance,” or “this edit was stopped.” Never turn any of those into a project-wide “protected” badge. See the [host coverage and limits](2026-11-11-host-coverage.md). |

## The proposed experience

1. **Start where the person already builds.** In a browser, offer one copyable card with the exact destination. For instance, [Lovable personal instructions](https://docs.lovable.dev/features/knowledge#personal-instructions) apply across the person's projects in one workspace, are available on all plans and need no admin access. In a project folder, let the existing coding assistant perform one transparent setup using the official package. Start with local Git checks; offer only the relevant editor integration. Preserve existing settings, show how to remove it, and establish coverage separately for each clone or new environment.
2. **Check one thing the builder cares about.** Someone asks for a saved list. An ordinary completion could say: “I added an item and reloaded the page. It was still there.” Only say this if the action was observed. If the host cannot perform it: “I changed the form. I couldn't test saving here. Add an item, reload, and see whether it stays.” An instruction can request that behavior; a receipt from an executed test or an observed interaction supports it. Do not run arbitrary project code just because a test script exists.
3. **Speak up at the point where it changes the outcome.** A useful local interruption: “I stopped this commit. This change could put a private key in visitors' browsers. Move the key to the server, then retry.” Give the current assistant the same redacted location and repair. Check the corrected change against the same rule. Allow a harmless change quietly. Say “I couldn't check this file” when it was unreadable or out of bounds.
4. **Make recovery mean what people think it means.** Offer the host's existing history first. Only offer Fence restore once it can show the files and changes it would restore, preserve unrelated work, and put the intended contents back. Disclose what cannot be recovered: a Git snapshot does not revoke a credential, unsend a message or restore an external database.

“Constant” means the builder does not have to remember to invoke Fence at a supported event. It does **not** mean collecting every keystroke or observing a closed builder's Publish button. “Free” means no Fence account, subscription, API key, per-check inference or remote service; distribution can require a download and the user's existing coding tool retains its own pricing. To keep the promise affordable, maintain one local engine, a handful of fixed repair messages and a short list of integrations we can actually retest. No background service is required for the first release.

## What to keep, remove and prove

| Decision | Scope of the proposed first release |
| --- | --- |
| **Keep** | The local runtime; staged and outgoing scans; fixed impact and remediation text; explicit incomplete results; reversible install; bounded fixtures plus the [known misses](../../tests/benches/KNOWN-GAPS.md). Start with the already demonstrable browser-exposed secret and credential-in-Git cases. Keep other rules under evaluation rather than deleting the test evidence. |
| **Remove from the shipped product** | Meta/Muse inference clients, model selection and escalation, API keys, contributor/provider settings, remote DB probes, demo profiles and hackathon messaging. Keep historical provenance in the archive. “Explain” can be a local sentence. No new model, MCP server, database connection, dashboard or cloud account is needed. |
| **Change the defaults** | No four-editor fallback, no profiles or teaching dial to pick, no whole-folder block on an unrelated commit. Show one consequence, one repair and the actual result. Separate “guidance saved,” “Git check ran” and “editor blocked this action.” Keep unsupported or stale integrations visibly unverified. |
| **Defer** | More adapters, a new scanner engine, automatic file restoration, and a branded publish verdict. Promote an editor only after a safe allow → block → repair rehearsal in that real host/version. A tracked file or successful local diagnostic is insufficient. |

**Next decision:** pilot **Claude Code plus local Git** and **Lovable with no terminal**, alongside each host's normal workflow. Claude Code already has an adapter worth proving; Lovable offers a way to try persistent guidance today. Neither choice is a claim of market share. The [pilot](2026-11-11-companion-pilot.md) includes the exact text, tasks, success measures and stop conditions. Before release, also require an install/upgrade/uninstall check that preserves prior settings, a network-disabled run of the installed core, benign changes that stay unblocked, an unavailable-check result that cannot appear as a pass, and platform-specific evidence for each OS claimed. Keep per-version results public without storing anyone's code, credentials or chat history.

If only the local cohort benefits, ship an excellent local tool and describe browser use as guidance. If people building in the browser get all the value from their host's existing checks and a short card, give them the card for free. If neither group can verify or repair a change more reliably than with the host alone, stop adding integrations and revisit the problem.
