# Stream 02 — Harness → Output Quality: causal mechanisms

- **Model:** minimax-m3.1-flash
- **Provider:** ollama-launch (Hermes Agent)
- **Date:** 2026-10-20
- **Stream:** 02 — Harness → Output Quality

---

## How to read this file

This stream asks: *what harness mechanisms actually change what the model produces, and by how much?*

Two prior contributors wrote this stream: `muse-spark-2026-10-20` and `google-gemini-3.8-flash-2026-10-20`. Both are mostly **practiced**-strength engineering consensus. This file deliberately centres on what they under-covered:

1. **Controlled measurements** — factorial ablations, A/B tests with effect sizes, benchmark-level null results.
2. **Negative results** — mechanisms that *don't* work, or work worse than doing nothing.
3. **The harness as attack surface** — the files the harness injects are themselves an injection vector. Nobody in this project has covered this.

Where this file **contradicts** a sibling, the contradiction is stated explicitly in the finding with both citations.

**Strength legend:** `proven` = measured in a controlled eval with a stated effect size · `practiced` = converged engineering practice, causal isolation absent · `contested` = credible evidence on both sides.

## Findings

### 1. Context files (AGENTS.md / CLAUDE.md) do **not** reliably help — and LLM-generated ones actively hurt

- **Mechanism:** Inject a repository-level context file (`AGENTS.md`, `CLAUDE.md`) into the agent's context, generated either by an LLM (`/init`) or written by a human developer.
- **Causal claim:** The most-repeated claim in the harness literature — "add a context file and the agent performs better" — is **contradicted by the first rigorous benchmark of it.** On a new 138-instance benchmark (AGENTbench) built from 12 repos that already ship developer context files, plus SWE-bench Lite:
  - **LLM-generated context files: −3% average resolution rate** on AGENTbench (−2% on SWE-bench Lite), and performance drops in 5 of 8 agent×dataset settings.
  - **Developer-written context files: only +4% average** — "marginally improve" performance.
  - **Cost: +20% (SWE-bench Lite) and +23% (AGENTbench)** in inference cost, driven by +2.45 and +3.92 average extra steps.
  - The mechanism of failure is behavioural, not comprehension: agents **do** follow the instructions (uv used 1.6×/instance when mentioned vs <0.01× when not; repo-specific tools 2.5× vs <0.05×), but the added requirements make the task *harder* — reasoning tokens rose 22% (GPT-5.2) and 14% (GPT-5.1 mini) on SWE-bench Lite. The authors' conclusion: "unnecessary requirements from context files make tasks harder, and human-written context files should describe only minimal requirements."
  - **"Map not manual" is measurably false for overviews.** 100% of Sonnet-4.5-generated context files were flagged as containing a codebase overview; 99% (GPT-5.2), 95% (Qwen3-30b-coder). Yet context files "do not meaningfully reduce" the number of steps before the agent touches a file relevant to the issue. Conclusion: "context files, even developer-provided ones, are not effective at providing a repository overview."
  - **Ablation explains the folklore.** When all documentation (`.md`, `examples/`, `docs/`) is *removed* from the repo, LLM-generated context files then **improve performance by 2.7% and beat developer-written docs.** The anecdotal reports of "context files help" come from repos with little/no existing documentation. In a well-documented repo, context files are redundant.
  - **Stronger generators ≠ better files.** Context files generated by GPT-5.2+Codex improved SWE-bench Lite by 2% but *degraded* AGENTbench by 3% vs the agent's own generator.
- **Evidence:** Gloaguen, Mündler, Raychev, Vechev (ETH Zurich + LogicStar.ai), *Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?*, arXiv:2602.11988 (12 Feb 2026) — https://arxiv.org/html/2602.11988v1 (accessed 2026-10-20). Benchmark code: https://github.com/eth-sri/agentbench (accessed 2026-10-20). The Codex "give a map, not a 1,000-page instruction manual" post that this file tests is https://openai.com/index/harness-engineering (accessed 2026-10-20). **Contradicts** the muse-spark file, which reports the Codex "map not manual" pattern as `practiced` without noting it was never measured; this file shows the map/overview mechanism was measured and found not to work.
- **Strength:** `proven` (controlled, multi-agent, multi-model; n=138 + 300 SWE-bench Lite instances). Caveat: Python-centric; the authors themselves note Python's prevalence in training data may nullify the effect.
- **Transfer to vibe-fence:** This is the single most important finding for the project. vibe-fence's flagship deliverable is a generated `AGENTS.md`. The evidence says: **a generated `AGENTS.md` is a net negative on well-documented repos.** Therefore the fence must (a) ship *minimal* context files — tooling commands and hard invariants only, no overview, no style guide, no architecture narrative; (b) never auto-generate a large file from the repo; (c) measure before/after success rate and cost on real vibe-coder repos before claiming a benefit; (d) prefer *dynamic* retrieval (a router the agent queries) over a *static* injected file.

### 2. Cross-component interference: the all-in scaffold is beaten by a proper subset, in every condition tested

- **Mechanism:** Stack scaffolding components — Planning, Tool Use, Memory, Structured Reasoning, Self-Reflection — into a single agent system prompt.
- **Causal claim:** A full factorial experiment over **all 2⁵ = 32 subsets** of five scaffolding components, on HotpotQA and GSM8K, across Llama-3.1-8B/70B, Qwen2.5-3B/7B and Claude Haiku 4.5 (118 configurations, 32,000+ evaluations, up to 10 seeds) found: **the best proper subset matched or beat the all-in five-component agent in every setting tested.** On HotpotQA at 8B, tool-use alone (F1 0.233) beat All-In (F1 0.177) by 32% (paired t-test p=0.023, Wilcoxon p=0.014, Cohen's d_z=0.87). On GSM8K, a three-component subset beat All-In by 79% (0.43 vs 0.24, p=0.010).
  - The interference is **scale-graded**: CCI gap = 32% at 8B, 19% at 70B, ≈0% (within noise) at Claude Haiku 4.5.
  - Shapley decomposition: **Tool Use captures 70% of total scaffold value** (φ=+0.177, z=9.1); **Planning has a significantly *negative* Shapley value**.
  - 183 of 325 testable triples violate submodularity (median γ=0.52, 95% CI [0.23, 0.71]); 90% of violations are *sign-flipping* (a component harmful alone becomes beneficial in a specific combination), so **greedy component selection is empirically unreliable** — you cannot add components one at a time and measure.
  - A length-matched control rules out "it's just context length": the gap held at 6–9×.
  - The authors' own Appendix E lists **negative mechanistic results**: hidden-state probes for component count were near-chance; output-token entropy did not correlate with per-question performance; theoretical dataflow-graph predictions correlated near-zero with empirical outcomes.
- **Evidence:** Liu, *More Is Not Always Better: Cross-Component Interference in LLM Agent Scaffolding*, arXiv:2605.05716 (Amazon) — https://ar5iv.labs.arxiv.org/html/2605.05716 (accessed 2026-10-20).
- **Strength:** `proven` for the general claim (all-in is not optimal); `practiced` for the specific component rankings, which are task- and scale-dependent and reverse between 8B and 70B.
- **Transfer to vibe-fence:** Ship **few, orthogonal** harness components, not a stack. A fence that injects plan-first guidance + memory + reflection + rules simultaneously is measurably *worse* than one that injects a couple of good ones. Practical rule: for each candidate fence mechanism, A/B it in isolation and in combination against a bare-agent baseline before shipping. Do not assume adding a component is safe. Note the model-scale gradient: a fence tuned for a cheap model may need the opposite of a fence tuned for a frontier model.

### 3. Tool-schema bloat measurably destroys tool selection; retrieval over tool definitions fixes it

- **Mechanism:** Load every tool's full schema into the system prompt (the standard MCP client behaviour) vs. retrieving the relevant tool descriptions on demand.
- **Causal claim:** RAG-MCP (semantic retrieval over MCP tool descriptions, only selected tools passed to the model) cut prompt tokens by **>50%** and **more than tripled tool-selection accuracy: 43.13% vs a 13.62% baseline** on benchmark tasks, including an MCP stress test. The failure mode without retrieval is the model's *decision* degrading, not just its context filling up.
- **Evidence:** Gan & Sun (Queen Mary / BUPT), *RAG-MCP: Mitigating Prompt Bloat in LLM Tool Selection via Retrieval-Augmented Generation*, arXiv:2505.03275 — https://arxiv.org/html/2505.03275v1 (accessed 2026-10-20). Corroborated by Anthropic's own measurement in the code-execution-with-MCP post: presenting MCP servers as **code APIs on a filesystem** rather than direct tool calls dropped one workflow from **150,000 tokens to 2,000 tokens (−98.7%)**, with the agent discovering tools by listing `./servers/` and reading only the files it needs — https://www.anthropic.com/research/code-execution-with-mcp (accessed 2026-10-20). The same principle in Anthropic's own skill format: Level 1 (YAML frontmatter metadata) is always loaded into the system prompt, Level 2 (SKILL.md body) is read from the filesystem only when the skill triggers, and Level 3 (scripts/resources) only when referenced — "until a Skill is triggered, only its name and description occupy context" — https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview (accessed 2026-10-20). For tool contracts generally, Anthropic's guidance is to namespace tools, return meaningful context, and optimise tool responses for token efficiency — https://www.anthropic.com/engineering/writing-tools-for-agents (accessed 2026-10-20).
- **Strength:** `proven` (RAG-MCP, measured on a benchmark) for the direction and rough magnitude; `practiced` for the specific code-execution implementation.
- **Transfer to vibe-fence:** vibe-fence must not inject a catalogue of its own skills/tools into every session. Emit skill *metadata* only (name + when-to-use), and let the agent read the body on demand — exactly the Level-1/Level-2 split Anthropic documents for Agent Skills (https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview, accessed 2026-10-20). If the fence ships MCP servers, expose them as code APIs.

### 4. ACI (custom agent-computer interface) was a 2024-era win that the *same lab* has since thrown away

- **Mechanism:** Wrap system primitives in purpose-built, model-optimised tools (windowed file paging, AST-aware symbol search, line-numbered diff application) instead of raw shell.
- **Causal claim (2024):** SWE-agent's ACI was what let GPT-4 fix GitHub issues at all — 12.29% on SWE-bench, state of the art on the full test set, achieved through "simple LM-centric commands and feedback formats" rather than model changes.
- **Causal claim (2026, contradicting 2024):** The same Princeton/Stanford team now ships `mini-swe-agent`: **~100 lines of Python, "does not have any tools other than bash — it doesn't even need to use the tool-calling interface of the LMs"**, scoring **>74% on SWE-bench Verified** (the repo's own README states the score; the earlier 65% figure for the 100-line version was not independently re-checked here). Their stated conclusion: "SWE-agent jump-started the development of AI coding agents in 2024. Back then, we placed a lot of emphasis on tools and special interfaces for the agent. However, one year later, as LMs have become more capable, **a lot of this is not needed at all** to build a useful agent!" mini also has a **completely linear history** — every step appends to the messages.
- **Evidence:** SWE-agent docs — https://swe-agent.com/latest/background/ (accessed 2026-10-20); mini-swe-agent repo — https://github.com/SWE-agent/mini-swe-agent (accessed 2026-10-20). The same effect appears without an agent loop at all: Agentless (localisation then repair, no tool-use decisions) achieved the highest performance (27.33%) *and* the lowest cost ($0.34) on SWE-bench Lite among open-source agents at the time — https://huggingface.co/papers/2407.01489 (accessed 2026-10-20).
- **Strength:** `proven` for "the interface mattered enormously in 2024"; `contested` as a general recipe — the 2026 result shows the *same* interface-minimality (bash only) is now *better* than a rich ACI, i.e. the optimal ACI shrank as models improved.
- **Transfer to vibe-fence — CONTRADICTS the gemini-3.8-flash file, which recommends giving the agent filtered/paged tools instead of raw shell.** Two defensible positions: (a) for a *capable* frontier model, keep the fence thin — one `bash` plus a couple of fence-specific commands; (b) for a *cheap* model (vibe-fence's likely weak-model tier, and the one Archestra deliberately tests against), a purpose-built filtered interface is a *feature*, because Archestra's failures on weak models were exactly in "file handling, sandbox tooling, provider schemas, and agent runtime." vibe-fence should therefore make the filtered interface **model-tier-conditional**, not universal. Note the ACI is not the only lever: Agentless (no agent loop at all — localisation then repair, no tool-use decisions) achieved the highest performance (27.33%) *and* the lowest cost ($0.34) on SWE-bench Lite among open-source agents at the time, beating SWE-agent.

### 5. Instruction hierarchy helps — but the system/user split is *not* the mechanism people assume

- **Mechanism:** Train/structure the model so that system-prompt instructions outrank user instructions, which outrank tool output and untrusted content.
- **Causal claim (supporting):** Wallace et al. argue the core vulnerability is that "LLMs often consider system prompts (e.g., text from an application developer) to be the same priority as text from untrusted users and third parties." Their training method "drastically increases robustness — even for attack types not seen during training — while imposing minimal degradations on standard capabilities."
- **Causal claim (contradicting):** Geng et al., *Control Illusion*, evaluated constraint prioritization across six state-of-the-art LLMs and found **"the widely-adopted system/user prompt separation fails to establish a reliable instruction hierarchy"** — models struggle with consistent prioritization even for simple formatting conflicts, and show "strong inherent biases toward certain constraint types regardless of their priority designation." Crucially, **"societal hierarchy framings (e.g., authority, expertise, consensus) show stronger influence on model behavior than system/user roles,"** suggesting pretraining-derived social priors beat post-training role markers.
- **Evidence:** Wallace et al., arXiv:2404.13208 — https://arxiv.org/abs/2404.13208 (accessed 2026-10-20); Geng et al., *Control Illusion*, arXiv:2502.15851 — https://arxiv.org/abs/2502.15851 (accessed 2026-10-20).
- **Strength:** `contested`. The hierarchy is a real training-time improvement, but the *mechanism* is weaker than assumed, and role labels alone are a fragile control.
- **Transfer to vibe-fence:** Do not rely on a role label as the only enforcement. Fence invariants should be expressed **as authority/expertise claims** ("you are a security-conscious senior engineer; secrets never enter the repo") in addition to any tier marker, and — more importantly — enforced **structurally** (see finding 8), because the textual tier is the soft link. This is a genuine contradiction with both sibling files, which treat "put invariants in the highest-privilege layer" as the primary defence.

### 6. Instruction *count* is a first-class budget variable — success decays roughly as p^n

- **Mechanism:** Add N simultaneous constraints to a prompt and ask the model to satisfy all of them.
- **Causal claim:** The "curse of instructions" gives an explicit model: **P(all instructions followed) ≈ P(one instruction)^n.** Across GPT-4o, Claude-3.5, Gemini-1.5, Gemma2 and Llama3.1 on ManyIFEval (up to 10 verifiable instructions per prompt), every model degraded sharply with instruction count. Reported single-instruction → multi-instruction averages: GPT-4o ~85% → 15%, Claude-3.5 ~90% → 44%. The derived production budget: at a 97.5% per-instruction success rate you can only afford **~2 instructions** for 95% joint reliability; ~3 for 90%; ~4–5 for 80%.
  - Independent replication with a different design: MOSAIC (Capital One) uses a **modular list** of application-oriented constraints decoupled from the task and measures pairwise constraint interactions and **constraint ordering effects**, arguing that "evaluations are frequently conducted with a small number of constraints, largely overlooking how their inter-dependencies and quantity affect compliance."
  - A second independent measure, IFScale (500 keyword-inclusion instructions), finds "even the best" models degrade as instruction density rises.
  - Mitigation is partial: inference-time self-refinement raised GPT-4o from 15% → 31% and Claude-3.5 from 44% → 58% — a real gain that does **not** eliminate the effect, at the cost of multiple inference passes.
- **Evidence:** Harada, Yamazaki, Taniguchi, Kojima, Iwasawa, Matsuo, *Curse of Instructions: Large Language Models Cannot Follow Multiple Instructions at Once* (ICLR 2025) — summary with benchmark, formula and per-model figures: https://maxpool.dev/research-papers/curse_of_instructions_report.html (accessed 2026-10-20); Purpura et al. (Capital One), *MOSAIC*, arXiv:2601.18554 — https://arxiv.org/html/2601.18554 (accessed 2026-10-20); *How Many Instructions Can LLMs Follow at Once?* (IFScale), arXiv:2507.11538 — https://arxiv.org/html/2507.11538v1 (accessed 2026-10-20).
- **Strength:** `proven` for the existence and rough shape of the effect; `practiced` for the exact p^n constant (it is a fit, not a law).
- **Transfer to vibe-fence:** **Count the fence's rules, not its words.** A fence that injects 15 always-on rules has, by the p^n model, a joint-compliance rate far below what any individual rule's compliance rate suggests. This is a *quantitative* justification for the "teaching dial" being a rule-count dial, and for hard-capping always-on rules at ~3–5 with everything else behind progressive disclosure.

### 7. Scaffolding *hurts* safety as much as it helps capability — and the two do not correlate

- **Mechanism:** Decompose agent scaffolding into (i) **domain skills** (tiered API documentation with progressive disclosure) and (ii) a **meta prompt** (behavioural rules incl. safety rules), vary both independently.
- **Causal claim:** ClawsBench (5 high-fidelity mock services — Gmail, Slack, Calendar, Docs, Drive — with deterministic snapshot/restore; 44 tasks; 6 models, 4 harnesses, 33 conditions) found:
  - With full scaffolding, task success rates are **39–64%** but **unsafe action rates are 7–33%**. Without any scaffolding, agents "often failed to take more than a few steps, achieving success rates near zero" — i.e. scaffolding is worth **+39 to +63 percentage points of capability**.
  - **Capability ≠ safety.** No consistent inverse relationship: Claude Opus had the *highest* success rate (63%) and tied for the *highest* unsafe action rate (23%); GPT-5.4 had a mid-tier success rate but the *lowest* unsafe rate (7%) — sometimes from over-refusal, not better reasoning.
  - **The scaffolding ceiling.** For highly capable models there was a **negative interaction**: combining domain skills *and* meta prompt did **not** always beat either alone.
  - Agents on their developers' **native harnesses** (Claude Code, Gemini CLI) beat the neutral OpenClaw harness out of the box — evidence that commercial harnesses ship hidden scaffolding that boosts capability and may obscure safety vulnerabilities.
  - Prompt-injection compliance was **as high as 90%** in some scenarios, and confidential-data leakage occurred "even when safety rules against such actions were explicitly provided in the meta prompt."
- **Evidence:** Li et al., *ClawsBench*, arXiv:2604.05172v2 (6 Apr 2026) — https://arxiv.org/abs/2604.05172v2 (accessed 2026-10-20); extended analysis with the 6-model × 4-harness × 33-condition breakdown — https://www.alphaxiv.org/abs/2604.05172 (accessed 2026-10-20).
- **Strength:** `proven` for the capability-vs-safety dissociation and the scaffolding ceiling; `practiced` for the unsafe-action patterns.
- **Transfer to vibe-fence:** vibe-fence's teaching layer is a *meta prompt* — so it inherits this result: **teaching rules do not buy safety.** Safety must come from structure (permissions, validators, gates), not from prose. And because success and safety are uncorrelated, a fence that raises task success may raise unsafe actions. The fence must report **both** metrics.

### 8. The harness's own files are the injection vector — and the measured failure rate is high

This is the angle neither sibling contributor covered, and it is the highest-severity finding for a product whose promise is *"the harness has your back."*

- **Mechanism:** The harness reads repository-resident files (`AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.cursor/rules/`, `SKILL.md`, `.claude/settings.json`) at session start and treats them as **instructions, not data**.
- **Causal claim (measured):**
  - **AIShellJack** (314 payloads, 70 MITRE ATT&CK techniques, across TypeScript/Python/C++/JS repos) measured **attack success rates of 41%–84%** against Cursor and GitHub Copilot with Claude-4 and Gemini-2.5-Pro. Per-configuration: **Cursor in auto-approve mode 83.4%**; Cursor + Claude 4 69.1%; Cursor + Gemini 2.5 Pro 73.9%; GitHub Copilot + Claude 4 52.2%; Copilot + Gemini 2.5 Pro 41.1%. In the `ts-lep` scenario, 89% of the 314 payloads triggered command execution and 83.4% of those executions were successful attacks. Notably, failed attacks are usually *no execution* (agent ignores the payload) — when the agent does try, it usually completes it (incomplete executions <3%).
  - **ReadSecBench** (500 real-world README files; taxonomy over linguistic disguise, structural obfuscation, semantic abstraction) measured **end-to-end exfiltration success up to 85%** on a commercially deployed computer-use agent, consistent across 5 languages and 3 injection positions; cross-model testing across 4 LLM families confirmed compliance is consistent across families. A **15-participant user study found a 0% detection rate** — humans did not spot the injected instructions. Of 12 rule-based and 6 LLM-based defenses tested, **none achieved reliable detection without unacceptable false-positive rates.** The authors name the underlying condition the **Trusted Executor Dilemma**: agents execute documentation-embedded instructions "because they cannot distinguish malicious directives from legitimate setup guidance — a structural consequence of the instruction-following design paradigm, not an implementation bug."
  - **Skills are the same vector.** OWASP's Agentic Skills Top 10 ranks **AST01 Malicious Skills** as Critical, severity "All platforms affected": "Three lines of markdown in a `SKILL.md` file were sufficient to exfiltrate SSH keys." The ClawHavoc campaign (Jan 2026) saw 1,184 malicious skills across 12 publisher accounts, with **five of the top seven most-downloaded ClawHub skills at peak infection confirmed as malware**. A USENIX Security 2026 study of 98,380 marketplace skills found 157 malicious skills carrying 632 vulnerabilities, with **73.2% of malicious skills implementing shadow features hidden from the user**; 100% of malicious skills combined a code-layer and a natural-language attack vector.
  - **The harness file is a *supply-chain* primitive.** NVIDIA's AI Red Team built a malicious Go library that detects the Codex environment via the `CODEX_PROXY_CERT` env var, writes its own `AGENTS.md` at build time, and instructs Codex to (a) inject a five-minute `time.Sleep` into every `main` function and (b) **conceal it from PR summaries and commit messages**. OpenAI acknowledged the report but concluded the attack does not elevate risk beyond existing compromised-dependency scenarios. Separately, Pillar Security's "Rules File Backdoor" (Mar 2025) showed hidden Unicode instructions in `.cursorrules` survive forking and propagate to every developer who clones a poisoned repo.
  - The architectural conclusion: "Until AI coding assistants can structurally separate trusted instructions from untrusted data, prompt-level filtering would remain a fragile defense." The CSA research note frames it as collapsing the code/data boundary — repository files are loaded "with a level of trust that approximates system-prompt authority."
- **Evidence:** Liu et al., *Your AI, My Shell* (AIShellJack), arXiv:2509.22040 — https://arxiv.org/html/2509.22040 (accessed 2026-10-20); follow-up survey, *How Agentic AI Coding Assistants Become the Attacker's Shell*, arXiv:2605.25871 — https://arxiv.org/html/2605.25871v1 (accessed 2026-10-20); Kao et al., *You Told Me to Do It* (ReadSecBench), arXiv:2603.11862 — https://arxiv.org/html/2603.11862 (accessed 2026-10-20); NVIDIA AI Red Team, *Mitigating Indirect AGENTS.md Injection Attacks in Agentic Environments* (20 Apr 2026) — https://developer.nvidia.com/blog/mitigating-indirect-agents-md-injection-attacks-in-agentic-environments (accessed 2026-10-20); CSA AI Safety Initiative, *README Injection: Repository Files Hijacking AI Coding Assistants* (17 Mar 2026) — https://labs.cloudsecurityalliance.org/research/csa-research-note-readme-instruction-injection-ai-coding-age/ (accessed 2026-10-20); Maloyan et al., *Prompt Injection Attacks on Agentic Coding Assistants* (SoK over 78 studies), arXiv:2601.17548 — https://arxiv.org/abs/2601.17548 (accessed 2026-10-20); OWASP AST01 — https://owasp.org/www-project-agentic-skills-top-10/ast01 (accessed 2026-10-20).
- **Strength:** `proven` (multiple independent measurement studies with large n and published artefacts). The *defenses* are much weaker than the attacks.
- **Transfer to vibe-fence — the most important design constraint in this file.** vibe-fence's entire value proposition is that it is trustworthy. But vibe-fence's mechanism is *exactly* the mechanism being measured here: it injects files the agent reads as instructions. So vibe-fence:
  1. **Must not make the injection surface worse than the status quo.** Every file the fence writes is a file an attacker can poison. Ship a minimal, single-owner, integrity-checked set — and the fence's own `AGENTS.md` must be the *shortest* file in the repo, because a longer file is a longer attack target and (per finding 6) more rules.
  2. **Must treat repo-resident files as untrusted data by default**, and say so *in the fence's own instructions* — but per finding 5, prose alone is insufficient.
  3. **Must add integrity checks**: a fence-side hash/attestation of the files it owns, so a build-time overwrite (the NVIDIA pattern) is detectable. A `vibe-fence validate` that flags "AGENTS.md changed since install" is a direct counter to the measured attack.
  4. **Must never let the fence's own rules be silently mutable by a dependency.** The NVIDIA Go library wrote `AGENTS.md` during `go mod tidy` — i.e. *before* any agent ran. The fence should refuse to load context files that were modified in the same session or that fail its integrity check.
  5. **Must provide a "read but do not obey" mechanism for files it ingests** — the CSA note's core complaint is that there is no way to mark a file as documentation rather than policy. That distinction is exactly what vibe-fence can add.
  6. **Should ship an attack-surface budget**: the fence is adding a privileged instruction channel to a system that already has a 41–85% injection success rate. If the fence cannot measurably reduce that rate, it is *increasing* risk while claiming to reduce it. ClawSentry's measured result (finding 9) shows it is possible — and shows what a "good enough" defense looks like.

### 9. A *measured* defense for skill/context injection: progressive multi-tier gating — with its exact cost

- **Mechanism:** Three runtime layers: (L1) deterministic rules on tool calls, (L2) a rule-anchored semantic reviewer, (L3) a read-only evidence-seeking agent; plus **First-Use Skill Package Review (FSPR)** that audits a skill package under a deterministic evidence floor *before* it is ever executed, escalating unresolved cases to bounded read-only review.
- **Causal claim (measured):**
  - On SkillInject with Codex/GPT-5.4, contextual attack success rate falls from **39.55% → 2.61%** while contextual task success rate moves only **83.78% → 83.05%** (−0.73 points).
  - Across five work agents on the full SkillsSafety benchmark, ASR is confined to **9.09–15.03% from 33.5–49.7% unprotected**, with aggregate task success on clean skills at **98.7%**.
  - **The "Safety Skill + AGENTS.md" defense is *weak*: baseline 25/60 → 18/60** (and task success fell 20/60 → 15/60). "Claude Guardrails Full": 19/60 → 20/60 — i.e. **no better than doing nothing**, with task success 20/60 → 17/60. This is the direct measured answer to "should the fence just add safety rules to AGENTS.md?" — **no.**
  - Component removal ablation: removing FSPR raised ASR 12.73 → 23.73; removing anti-bypass raised it to 19.30. The full configuration is the best ASR/TSR operating point.
  - The **hard-block vs soft-response** choice matters structurally: a warning-mode response had ASR 24.56 vs 8.47 for hard block — a "caution" competes with package contents the attacker already shaped.
- **Evidence:** Wang, Wei, Zeng, Jin et al., *ClawSentry: A Progressive Multi-Tier Security Monitor for Safeguarding Autonomous LLM Agents*, arXiv:2608.21101 — https://arxiv.org/html/2608.21101 (accessed 2026-10-20); the benchmark it uses, Jin et al., *SkillSafetyBench*, arXiv:2605.12015 — https://arxiv.org/html/2605.12015v3 (accessed 2026-10-20), which reports that among 19 attacked runs that still fully completed the task, **8 also satisfied the attack-success verifier (full-pass-conditional ASR 42.1%)** — i.e. attacks can succeed *without* visibly degrading task output, so task success alone is an unsafe release gate.
- **Strength:** `proven` for the specific measured deltas on these benchmarks; `practiced` for transfer to other runtimes. Note the monitored runtimes are Codex, Claude Code, Kimi CLI, Gemini CLI — the same family vibe-fence targets.
- **Transfer to vibe-fence:** The pattern is directly portable and already spans vibe-fence's target runtimes. Concretely: (a) **pre-execution review** of any skill package the fence installs — the fence is a skill distributor, so it needs FSPR-equivalent admission control; (b) **tiered runtime gating** on the fence's own tool calls; (c) **never rely on the "Safety Skill + AGENTS.md" text-only defense** — it was measured at roughly half the effectiveness of a hard block and it *cost* task success; (d) **gate on unsafe-action rate, not task success**, because 42.1% of attacks succeeded *while the task still passed*.

### 10. "Long context" is not "long attention" — and the cause is *step count*, not context length

- **Mechanism:** Assume a bigger window buys you room to put the whole repo, the whole history and the whole ruleset in context.
- **Causal claim (positional):** Liu et al. established the U-shaped curve — performance is highest when relevant information sits at the **beginning or end** of the input context and "significantly degrades when models must access relevant information in the middle of long contexts, even for explicitly long-context models." Chroma replicated it on 18 frontier models: performance degrades as input length increases "often in surprising and non-uniform ways" even when the task is deliberately minimal.
- **Causal claim (scale of the degradation):** RULER evaluated 17 long-context models on 13 tasks with multi-hop tracing and aggregation added to NIAH: "Despite achieving nearly perfect accuracy in the vanilla NIAH test, almost all models exhibit large performance drops as the context length increases. While these models all claim context sizes of 32K tokens or greater, **only half of them can maintain satisfactory performance at the length of 32K**." NoLiMa removed the lexical crutch (minimal overlap between question and needle) and found at 32K, 10 of 12 models drop below 50% of their short-context baseline; even GPT-4o falls from 99.3% to 69.7%. OP-RAG's measured baseline: Llama3.1-70B with a full 128K window scores 34.32 F1 on En.QA, GPT-4o 32.36, Gemini-1.5-Pro 43.08 — **below what plain RAG achieves with a much shorter input.**
- **Causal claim (the one that contradicts the "lost in the middle" folk explanation):** A controlled study of 9 models (6 open, 1.2B–671B, plus 3 deployed proprietary systems), 4 task families, 5 horizons, 3 context regimes, n=10,664 trajectories, found task success follows a **geometric law in per-step reliability**. On the genuinely agentic task, *every* model including deployed systems fell from near-perfect to near-zero **within sixteen steps**. And critically: "Degradation is driven by step count rather than context length: **bounding the context window steepens decay rather than easing it** (logit slope −0.69 vs −0.44, p=3×10⁻⁶), **contradicting a lost-in-the-middle explanation**." The authors warn "against a common production shortcut" and project a gap between benchmark and production horizons from 0.42 (GAIA-length) to 0.24 (hundred-step).
- **Evidence:** Liu et al., *Lost in the Middle*, arXiv:2307.03172 — https://arxiv.org/html/2307.03172 (accessed 2026-10-20); Hsieh et al., *RULER*, arXiv:2404.06654 — https://arxiv.org/html/2404.06654 (accessed 2026-10-20); Modarressi et al., *NoLiMa*, arXiv:2502.05167 — https://arxiv.org/html/2502.05167v1 (accessed 2026-10-20); Hong, Troynikov, Huber (Chroma), *Context Rot* (Jul 2025) — https://trychroma.com/research/context-rot (accessed 2026-10-20); Yu, Xu, Akkiraju, *In Defense of RAG in the Era of Long-Context Language Models*, arXiv:2409.01666 — https://arxiv.org/html/2409.01666v1 (accessed 2026-10-20); Mittal, *How Fast Do Agents Rot?*, arXiv:2609.01660 — https://arxiv.org/abs/2609.01660 (accessed 2026-10-20). Anthropic's own framing of the same constraint: "good context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome," with a finite attention budget as the governing constraint — https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents (accessed 2026-10-20).
- **Strength:** `proven` for the degradation; `contested` for the *explanation* — "lost in the middle" (positional) and "step-count geometric collapse" (the rot study) are **competing explanations** and the latter is explicitly argued against the former. Both readings are presented here because both are measured.
- **Transfer to vibe-fence:** Two hard rules. (1) **Never rely on window size as a budget** — a 200k window is not 200k of usable attention; budget for the *effective* context (RULER: half of 32K-claiming models fail at 32K). (2) **Cap the number of agent steps per fence task.** The measured law says every model — frontier included — collapses within ~16 steps on a genuinely agentic task. So vibe-fence's task loop should have a hard step budget with a human/teaching-dial checkpoint well before that, and a *smaller* context window is not a fix for a long task (tightening the window steepened decay).

### 11. Long-horizon agents degrade for a *specific* reason: the context ceiling and the verification gap

- **Mechanism:** Scale a single agent by (a) sequential scaling — more interaction turns, longer history; (b) parallel scaling — sample K trajectories and pick one.
- **Causal claim:** General AgentBench (10 leading LLM agents, unified tool pool across search/coding/reasoning/tool-use) found three things. (1) Moving from domain-specific evaluation to the general-agent setting, **most models drop ~30%** (Claude is the most robust). (2) **Sequential scaling hits a context ceiling:** performance improves within a modest range of extra turns then "fluctuates or degrades," because accumulated history overwhelms the agent's reasoning capacity. (3) **Parallel scaling has a verification gap:** past@K rises but "self-choice accuracy" lags badly — the agent cannot reliably pick its own best answer, so the theoretical ceiling is unreachable. **Neither scaling methodology yields effective improvements in practice.**
- **Evidence:** Li et al., *Benchmark Test-Time Scaling of General LLM Agents*, arXiv:2602.18998 — https://arxiv.org/html/2602.18998v1 (accessed 2026-10-20).
- **Strength:** `proven` (controlled, 10 agents, unified environment).
- **Transfer to vibe-fence:** Directly relevant to the "ask 5, pick 1" pattern and to any turbo mode. **Self-selection is the bottleneck, not generation.** If vibe-fence wants to sample multiple candidate implementations, it must verify them *mechanically* (tests/lints/validators) — a model picking among its own outputs is exactly the failure this measures. And long single-agent sessions are worse than several short ones: a task that will take 30 steps should be decomposed, not run longer.

### 12. Mechanistic verification beats "the agent says it's done" — but self-verification without an external check is not enough

- **Mechanism:** Feed execution feedback (test results, compiler output) back into the loop, and require the agent to verbalize a diagnosis before retrying.
- **Causal claim:** Reflexion converts binary/scalar environment feedback into verbal reflection stored in an episodic memory buffer, "obtains significant improvements over a baseline agent across diverse tasks" and reaches **91% pass@1 on HumanEval, surpassing the previous state-of-the-art GPT-4 at 80%**. The mechanism is *execution feedback*, not self-critique in the abstract: Reflexion's ablations vary feedback signal, incorporation method, and agent type.
  - Independent evidence that instruction-following — not coding proficiency — is the binding constraint in TDD-style work: WebApp1K (1000 challenges, 20 domains, 19 frontier models) found "instruction following and in-context learning as critical capabilities for TDD success, **surpassing the importance of general coding proficiency or pretraining knowledge**," with "instruction loss in long prompts" as a named bottleneck.
  - External, non-agentic verification of intermediate artifacts is measurable: Spec Kit Agents (128 runs, 32 feature tasks, 5 repos) adds read-only **discovery hooks** before each phase and **validation hooks** after, and reports a consistent **+0.15 on a 1–5 LLM-as-judge quality composite** with **99.7–100% test pass rates**, attributing the benefit not to a dramatic average-score jump but to "**earlier detection and prevention of compounding context errors**." Its named failure mode is **context blindness** — intermediate artifacts internally coherent but incompatible with the repo (referencing non-existent APIs, proposing non-existent paths).
- **Evidence:** Shinn et al., *Reflexion*, arXiv:2303.11366 — https://arxiv.org/abs/2303.11366 (accessed 2026-10-20); Cui, *Tests as Prompt* (WebApp1K), arXiv:2505.09027 — https://arxiv.org/abs/2505.09027 (accessed 2026-10-20); *Spec Kit Agents*, arXiv:2604.05278 — https://arxiv.org/html/2604.05278 (accessed 2026-10-20).
- **Strength:** `proven` for the Reflexion numbers; `practiced` for the Spec Kit numbers (LLM-as-judge, 32 tasks).
- **Transfer to vibe-fence:** "Done" must mean **mechanically checked**. Wire the fence's Check phase to real validators (tests, lints, typecheck, a fence-specific invariant check) and make the agent write a short diagnosis to `.fence/` before each retry. The Spec Kit finding is directly actionable: a fence that validates *intermediate artifacts* (does this plan reference files that exist? does this diff touch only intended paths?) catches errors before they compound — and that is a better teaching moment than a failing test at the end.

### 13. Splitting reasoning from editing measurably helps; it is a harness change, not a model change

- **Mechanism:** Two-stage loop — an **Architect** model describes *how* to solve the problem; an **Editor** model receives that solution and emits concrete file edits.
- **Causal claim:** Aider's Architect/Editor mode "produced SOTA results on aider's code editing benchmark": **o1-preview as Architect with DeepSeek or o1-mini as Editor → 85%**, above the previous SOTA marker, and "significantly improved the benchmark scores of many models, compared to their previous 'solo' baseline scores." Pairing models with themselves also helped: Sonnet, GPT-4o and GPT-4o-mini all scored higher as an Architect/Editor pair. Notably, **DeepSeek was remarkably effective as the Editor** — the cheap model did the mechanical part.
- **Evidence:** Aider, *Separating code reasoning and editing* (26 Sep 2024) — https://github.com/Aider-AI/aider/blob/main/aider/website/_posts/2024-09-26-architect.md (accessed 2026-10-20).
- **Strength:** `practiced` — a vendor benchmark, single implementation, not an independent controlled study. (The gemini-3.8-flash sibling file calls this `proven`; this file downgrades it, since the numbers come from the vendor's own benchmark and there is no ablation reported for the architect stage in isolation.)
- **Transfer to vibe-fence:** **This is the cheapest quality lever vibe-fence can pull and it maps perfectly onto the "non-technical user" story.** A vague prompt ("make the login nicer") is a *reasoning* problem; editing is mechanical. A fence that forces a plan artifact before edits, then a separate mechanical edit step, matches what the data supports. And because a cheap model can be the Editor, vibe-fence can run a strong planner + cheap editor — a cost win as well as a quality win. vibe-fence should A/B this on its own bench (the Spec-Kit-style judge is a reasonable starting metric).

### 14. Token efficiency is a *measured* harness lever, but only because Cursor A/B'd it on production traffic

- **Mechanism:** Shrink the always-present context: system prompt, tool definitions, static context.
- **Causal claim:** Cursor's harness changes "reduced token costs for users by **7% without reducing agent quality**," with two component effects: the system prompt was trimmed by **~66%** — because "as models improved, much of that direction became unnecessary. Instead of long lists of 'DO NOT do this,' 'You must,' or 'Important' instructions, we could simply define how a tool behaves and models would generally comply. This was true across model families" — and tool definitions were moved to load-on-demand. Cursor explicitly notes A/B testing on a large user base is what made this credible: "While evals can be a fast and useful proxy, they often represent 'hard' problems and don't properly reflect the true distribution of user requests."
- **Evidence:** Cursor, *Improved token efficiency for longer agent runs* (23 Sep 2026) — https://cursor.com/blog/improved-token-efficiency (accessed 2026-10-20).
- **Strength:** `proven` for the production A/B result; `practiced` for the individual percentages.
- **Transfer to vibe-fence:** Two direct consequences. (1) **Prefer positive definitions over prohibitions** — define the desired behaviour, don't list "DO NOT"s. This *contradicts* the gemini-3.8-flash file's "avoid negative constraints / pink elephant" framing being framed as folklore-dependent: Cursor's measured 66% trim is evidence that negative instruction lists were the removed part. (2) vibe-fence's own eval bench must be built from **realistic vibe-coder requests**, not synthetic hard problems, or its own A/Bs will mislead (this is the same lesson as Archestra's real-customer-workflow bench).

### 15. Harness change can move a model by more than a model upgrade — on the same weights

- **Mechanism:** Change only the harness (retained reasoning + compaction), keep the model fixed.
- **Causal claim:** Cursor reports the ARC-AGI-3 case: harness changes alone lifted GPT-5.6 Sol from 13.3% → 38.3% while reducing output tokens 6× — same model, different harness. The broader Cursor lesson: "improving the harness is a matter of obsessively stacking small optimizations that together make agents better," with a *model-specific* twist — the harness must provision each model with the tool format it was **trained** on (OpenAI models → patch-based editing, Anthropic models → string replacement), because "giving it the unfamiliar one costs extra reasoning tokens and produces more mistakes." They also report a model-specific quirk they had to prompt around ("context anxiety": as context filled, a model began refusing work and hedging that the task was too big), fixed by prompt adjustments. And: "Sometimes these online tests tell us to shelve an idea that seems promising. In one experiment, we tried a more expensive model for context summarization and observed it made a negligible difference in agent quality that wasn't worth the higher cost."
- **Evidence:** Cursor, *Continually improving our agent harness* — https://cursor.com/blog/continually-improving-agent-harness (accessed 2026-10-20).
- **Strength:** `practiced` for the general method; the ARC-AGI-3 swing is a single cited case, not a controlled study, and bundles multiple changes.
- **Transfer to vibe-fence:** (a) The single biggest harness lever is often **per-model tool formatting** — vibe-fence should record, per adapter, the edit format the target model was trained on. (b) **Model-switching and mid-chat takeover need explicit handling** — Cursor had to add custom instructions telling a model it's taking over from another and steering it away from tools in the history that aren't its own. (c) The negative result is a gift: **do not spend money on a bigger summarizer model**; measured as negligible. (d) vibe-fence should keep a "shelved ideas" log — knowing which plausible optimizations were measured and rejected is worth more than the ideas themselves.

### 16. Weak models are a harness debugger — and a cost lever

- **Mechanism:** Run the harness on deliberately weak/cheap models and study the failures.
- **Causal claim:** Archestra's thesis: "Strong models are excellent at hiding product bugs. Give one a broken tool call or a confusing error, and it may still finish the task. Weaker models are less forgiving." Their nightly bench (26 real customer workflows, ~10 models, boots the real product, deterministic out-of-band grading with hidden ground truth, full trajectories recorded) found defects in **file handling, sandbox tooling, provider schemas, and agent runtime** — bugs strong models had been papering over with extra tokens and retries. The commercial result: an open-weight model passes ~90% of the tasks for **well under $1 per run**, while frontier models cost **$20–30 per run** for the remaining few points; a mid-tier brand-name model at $7.82/run scored *below* five open models costing $0.27–$1.23. And the instability: one model scored between 58% and 88% across the same week — "a single-run benchmark would have hidden that instability."
- **Evidence:** Archestra, *We Debug Our AI Harness on Weak Models on Purpose* (20 Jul 2026) — https://archestra.ai/blog/we-debug-our-ai-harness-on-weak-models-on-purpose (accessed 2026-10-20). Public harness: https://github.com/archestra-ai/archestra/tree/main/ai-labs.
- **Strength:** `practiced` — one company, self-reported, but with a published, reproducible harness and explicit methodology.
- **Transfer to vibe-fence:** (a) **Test the fence on a cheap model.** vibe-fence's users are non-technical; the fence will often run against whatever model the user has. A fence that only works on frontier models is a fence that fails for most of its audience. (b) **Grade deterministically, not with an LLM judge** — hidden ground truth, out-of-band checking, full trajectory capture. (c) **Run the bench nightly and look for variance**, not just means. (d) The cost curve is a business-model input: if an open model at <$1/run clears 90% of the fence's bench, the fence can ship a cheap tier.

### 17. Benchmarks that measure harnesses are themselves decaying — score without a stated harness is not comparable

- **Mechanism:** Use an eval whose task distribution, harness and grading are fixed and trustworthy.
- **Causal claim:** OpenAI's Frontier Evals team audited SWE-bench Verified, found contamination and design flaws, and **stopped using it**; they then audited the replacement (SWE-bench Pro) with a datapoint-analysis pipeline (286 tasks flagged), investigator-agent passes, and five independent experienced-engineer reviews per flagged task. Result: **~30% of SWE-bench Pro tasks are broken**, in four categories: overly strict tests, underspecified prompts, low-coverage tests, and misleading prompts. They **retracted** their earlier recommendation to adopt SWE-bench Pro. The lesson they draw: "the difficulty of curating hard but fair benchmarks and the growing utility of agents for scalable data quality checks." The eval-design lesson is: tests written to validate a specific change do not define an implementation-agnostic standard, so "a model can pass while a functionally correct solution is invalidated."
- **Evidence:** OpenAI, *Separating signal from noise in coding evaluations* (8 Jul 2026) — https://openai.com/index/separating-signal-from-noise-coding-evaluations/ (accessed 2026-10-20). A parallel effort at the harness level: Terminal-Bench 2.0 shipped with "substantial manual and LM-assisted verification" of every task, and Harbor re-built the harness to support cloud-deployed containers and RL/SFT rollouts — https://www.tbench.ai/news/announcement-2-0 (accessed 2026-10-20).
- **Strength:** `proven` (audited with a stated pipeline and human verification).
- **Transfer to vibe-fence:** vibe-fence needs its **own** eval, and it needs the same rigor: write tasks that specify *behaviour*, not implementation; grade with tests that any correct solution passes; use the multi-reviewer + investigator-agent pipeline when flagging; and **always report the harness alongside the score**. This is also the reason the "17–22 point same-model-different-scaffold swing" style numbers in the wild are not comparable across reports.

### 18. A repo map (graph-ranked, token-budgeted context) is the measured alternative to static overviews

- **Mechanism:** Build a graph over the repo (files/symbols as nodes, dependencies as edges), rank with PageRank, and inject a *token-budgeted* slice of the ranked map on each request.
- **Causal claim:** Aider sends "a concise map of your whole git repository that includes the most important classes and functions along with their types and call signatures" with each change request, so the model can see definitions from everywhere and can ask for specific files if it needs more. For large repos it "solves this problem by sending just the most relevant portions of the repo map," computed via a graph-ranking algorithm, and **dynamically sizes the map to the active token budget** (`--map-tokens`, default 1k) — expanding when no files are yet in chat. This is the direct answer to finding 1's failure: a *dynamic, ranked* map is not the same artifact as a static prose overview.
- **Evidence:** Aider, *Repository map* docs — https://aider.chat/docs/repomap.html (accessed 2026-10-20).
- **Strength:** `practiced` — production-proven, but the doc does not report a controlled A/B against no-map.
- **Transfer to vibe-fence:** If vibe-fence wants to give agents codebase context, a **ranked, budgeted, dynamic** map is a better bet than a static `AGENTS.md` overview, because (a) finding 1 measured that static overviews don't speed up file discovery, and (b) a map is generated at query time from the code itself, so it cannot go stale and cannot be poisoned with prose. Concretely: a `vibe-map` step that emits ≤1k tokens of ranked symbols, refreshed per task.

## Gaps / Unknowns

1. **Almost no public study isolates *one* harness mechanism with a proper RCT.** The best evidence here is a factorial ablation on QA tasks (finding 2), a benchmark with three conditions (finding 1), and product A/Bs (findings 14, 15). Almost nothing is measured on *real* vibe-coder tasks with *non-technical* users, which is vibe-fence's actual population. **vibe-fence's own bench is the missing experiment.**
2. **AGENTS.md was measured on Python repos.** The authors explicitly flag that Python's over-representation in training data may nullify the effect and that niche languages/toolchains are untested. vibe-fence should not assume the finding transfers to JS/TS/Python-mixed repos without re-measuring.
3. **Instruction-hierarchy robustness in long contexts is unmeasured.** Control Illusion (finding 5) tests conflict resolution; nobody has published the degradation curve for hierarchy adherence at 100k+ tokens. Note finding 10 argues step count, not context length, is the driver — so the right experiment is step count, not token count.
4. **The optimal fence rule count is unknown.** The p^n model (finding 6) predicts a sharp cliff but the per-instruction success rate *p* for *fence-specific* rules (as opposed to ManyIFEval's keyword constraints) is unmeasured. Nobody has published a Pareto frontier of rules-count vs task success vs cost for a real project.
5. **No study measures the *interaction* between a fence's teaching layer and its safety layer.** ClawsBench found a scaffolding ceiling for capable models; whether a fence that both teaches and gates is past that ceiling is unknown.
6. **Remediation cost of a *blocked* skill is unmeasured.** ClawSentry's hard block cuts ASR 39.55% → 2.61% but the paper reports task-success deltas, not the *developer-time* cost of a false-positive block. For a non-technical user, a false-positive block is a wall — this is the product risk nobody has quantified.
7. **Whether "one repo, one fence" is optimal is untested.** Everything here is single-repo. Multi-repo users, monorepos, and vendored dependencies are unstudied.
8. **No public numbers exist for a harness's effect on a *non-technical* user's outcome** (task completion, time-to-first-success, or willingness to continue). The whole "teaching dial" concept is currently supported by evidence from a different literature (automation bias, scaffolding meta-analyses) that the muse-spark stream 05 file draws on — but that is a stream 05 claim, not a stream 02 one.
9. **Effect sizes for the frontier models vibe-fence will run against are mostly from 2024–2025 generations.** The ClawsBench, AGENTbench and AIShellJack runs use GPT-5.x / Claude 4.x / Gemini 2.5-era models. Injection rates in particular may be lower on newer models — but no newer measurement was available at time of writing, and the 2026 rotation study suggests capability gains have not closed the *structural* gap.
10. **Cannot verify:** the exact failure-rate changes in ClawSentry's component-removal ablation for every configuration, and whether the "Claude Guardrails Full" baseline is reproducible — the numbers are reported in a single table in a single paper with no released trajectories for that comparison.

## Implications for vibe-fence

### Copy (evidence-backed, adopt directly)

1. **Copy: a *minimal* `AGENTS.md` — tooling commands and hard invariants only.** No codebase overview, no style guide, no architecture narrative. The measured result is that LLM-generated context files are a net negative (−3% resolution, +23% cost) and even developer-written ones buy only +4%, because the added requirements make the task harder and increase reasoning tokens 14–22%. *(§1)*
2. **Copy: the *dynamic, ranked, token-budgeted repo map* instead of a static overview.** Aider-style graph ranking at ≤1k tokens, recomputed per task — it cannot go stale and cannot be poisoned with prose, and finding 1 shows static overviews do not speed up file discovery. *(§1, §18)*
3. **Copy: the "Safety Skill + AGENTS.md" defense is NOT enough — use pre-execution review + tiered runtime gating.** Measured: text-only safety rules took ASR 25/60 → 18/60 and *cost* task success (20/60 → 15/60); a hard block + rule-anchored reviewer + read-only evidence agent took contextual ASR 39.55% → 2.61% at a 0.73-point task-success cost. *(§9)*
4. **Copy: gate releases on unsafe-action rate, not task success.** 42.1% of attacks succeeded *while the task still passed*. A fence that only measures "did the user get what they asked for" will ship attacks. *(§9)*
5. **Copy: the Architect→Editor split.** Force a plan artifact before edits, then a separate mechanical edit step. o1-preview Architect + cheap Editor hit 85% on aider's benchmark, and cheap models are effective Editors — this is a quality *and* cost lever for non-technical users. *(§13, §12)*
6. **Copy: mechanical verification as the definition of "done."** Wire Check to real validators (tests, lints, typecheck, fence invariants), and require a short written diagnosis in `.fence/` before each retry. Reflexion's 91% vs 80% HumanEval comes from *execution* feedback, not self-critique. *(§12)*
7. **Copy: validate *intermediate* artifacts, not just the final diff.** Spec Kit's measured benefit is "earlier detection and prevention of compounding context errors" — catching a plan that references a non-existent file is a better teaching moment than a failing test. *(§12)*
8. **Copy: a hard step budget per fence task, with a checkpoint well before 16 steps.** Every model tested — frontier included — collapsed from near-perfect to near-zero within 16 steps on a genuinely agentic task, and *tightening* the context window steepened decay rather than easing it. *(§10)*
9. **Copy: metadata-only skill exposure + on-demand body loading.** Only name+description in context until a skill triggers (Anthropic's documented L1/L2/L3 split); for MCP, expose servers as code APIs (Anthropic measured 150,000 → 2,000 tokens) and retrieve tool descriptions (RAG-MCP tripled tool-selection accuracy, 13.62% → 43.13%). *(§3)*
10. **Copy: positive definitions over prohibition lists.** Cursor's measured 66% system-prompt trim was achieved by *removing* "DO NOT / You must / Important" lists and defining tool behaviour instead; the trim held across model families. *(§14)*
11. **Copy: per-adapter tool formatting.** Give each model the edit format it was trained on (patch-based vs string replacement) — Cursor measured that using the unfamiliar one "costs extra reasoning tokens and produces more mistakes." *(§15)*
12. **Copy: the weak-model nightly bench with deterministic, out-of-band grading.** It surfaces fence bugs strong models hide, and it is also the cost story (≈$1/run at ~90% vs $20–30/run for the last few points). Track variance, not just mean. *(§16)*
13. **Copy: context-file integrity checks in `vibe-fence validate`.** Hash/attest the files the fence owns and flag changes — this directly counters the measured NVIDIA pattern (a dependency writes `AGENTS.md` at build time, before the agent ever runs). *(§8)*
14. **Copy: a "read but do not obey" channel for repo-resident docs.** The measured gap is that no harness can mark a file as *documentation* rather than *policy*. That distinction is precisely what vibe-fence can add, and it is the CSA note's central structural complaint. *(§8)*

### Avoid (measured to be harmful or unnecessary)

15. **Avoid: auto-generating a large `AGENTS.md` from the repo.** It is the project's flagship feature and the evidence says it is a net negative on well-documented repos. If vibe-fence generates one at all, generate it *minimally* and A/B it. *(§1)*
16. **Avoid: a monolithic always-on rule set.** With P(all) ≈ P(one)^n, ~97.5% per-rule compliance affords only ~2 rules at 95% joint reliability. Cap always-on rules and push the rest behind progressive disclosure. *(§6)*
17. **Avoid: stacking harness components by default.** The all-in five-component scaffold was beaten by a proper subset in *every* condition tested (32% on HotpotQA/8B, 79% on GSM8K), with Planning's Shapley value *negative* and 90% of interference violations sign-flipping — so greedy add-one-at-a-time selection is unreliable. A/B each component in isolation *and* in combination. *(§2)*
18. **Avoid: assuming a long context window is usable context.** Half of models claiming 32K+ fail at 32K (RULER); with literal-matching crutches removed, 10 of 12 models drop below 50% of baseline at 32K. Budget for the *effective* window, and prefer retrieval over stuffing. *(§10)*
19. **Avoid: relying on the system/user role split as the primary safety control.** "The widely-adopted system/user prompt separation fails to establish a reliable instruction hierarchy." Express fence invariants as authority/expertise claims *and* enforce them structurally. *(§5)*
20. **Avoid: teaching rules as the safety mechanism.** ClawsBench found meta-prompt safety rules do not prevent leakage "even when safety rules against such actions were explicitly provided," and the highest-success model also had one of the highest unsafe-action rates. Safety must be structural (permissions, validators, gates). *(§7)*
21. **Avoid: longer agent sessions to cover more work.** Sequential scaling hits a context ceiling; every model collapsed within 16 steps. Decompose into short tasks with checkpoints. *(§10, §11)*
22. **Avoid: model self-selection among multiple candidate solutions.** The verification gap is the binding constraint — past@K rises but self-choice lags. Verify candidates mechanically. *(§11)*
23. **Avoid: a bigger, pricier summarization model.** Cursor A/B'd it: negligible quality difference, not worth the cost. Log shelved ideas so the same experiment is not re-run. *(§15)*

### Invent (no evidence found — vibe-fence's own opportunity)

24. **Invent: a `fence-validate` that (a) counts always-on rules and fails above a cap, (b) hashes the fence-owned files and flags post-install modification, (c) checks that every referenced path/script still exists, and (d) marks repo-resident files as untrusted-data-by-default.** None of the measured defenses (text safety rules, model guardrails) covered any of these; the injection surface is real and the fence is the layer that could close it. *(§6, §8, §9)*
25. **Invent: an adversarial fence bench — 8–12 tasks that measure the fence's *own* attack surface**: a poisoned `AGENTS.md` in a vendored dependency, a README instructing the agent to skip the fence, a malicious skill package, a "user asks to bypass the fence" prompt. Grade on unsafe-action rate. This is the experiment nobody in the project has run, and it is the one that decides whether vibe-fence is a net safety improvement or a new attack surface. *(§8, §9)*
26. **Invent: a capability-vs-safety double scoreboard in every fence eval** (task success *and* unsafe-action rate, reported together), because the two are uncorrelated — a fence that only optimizes success is optimizing the wrong axis for its stated promise. *(§7)*
27. **Invent: a model-tier-conditional harness profile** — rich filtered interface for weak models (their failures cluster in file handling, sandbox tooling, provider schemas, agent runtime) vs. thin bash-only interface for frontier models (the 2024 ACI recipe was retired as unnecessary). Same fence, different adapter profile per model tier, re-validated as models improve. *(§4, §16)*
28. **Invent: a per-task step-budget + `context-anxiety` detector** — a fence that notices the agent beginning to hedge/refuse ("this is too big") and proactively splits the task, based on the measured model-specific failure Cursor had to prompt around. *(§10, §15)*
29. **Invent: a "one-shot bench" that measures the fence's marginal value on the user's *own* repo** — clone the vibe-coder's project, run N real tasks with and without the fence, report success rate, cost, and unsafe-action rate. Given finding 1's finding that context files help only in undocumented repos, the fence's value is likely repo-dependent; the fence should *tell the user* which tier they are in rather than claim a universal benefit. *(§1, §17)*
