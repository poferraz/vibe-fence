## 2. Where they disagree

### D-01 — Should the OWASP anchor be the 2021 or 2025 category set?

- **Reading A (muse-spark, gemini-3.8-flash):** Uses OWASP Top 10:2025 (muse-spark) or OWASP 2021 (gemini) as the category frame — e.g. gemini cites `A06:2021 Vulnerable Components`, `A01:2021 Broken Access Control`. Muse-spark correctly names 2025 but interpolates several claims against the generic `top10.owasp.org/2025/` landing page rather than per-category pages.
- **Reading B (minimax, gpt-6):** Anchors to **OWASP Top 10:2025** per-category pages and is explicit that 2021→2025 changed the shape: A03:2025 *Software Supply Chain Failures* replaced A06:2021 (no longer "known CVEs" but an ecosystem of build/distribution/dependency risks — https://top10.owasp.org/2025/A03_2025-Software_Supply_Chain_Failures/); SSRF folded into A01:2025; A10:2025 *Mishandling of Exceptional Conditions* is new. Minimax publishes a full introduction-page quote table; gpt-6 publishes an OWASP 2025 risk↔rule coverage map.
- **Resolution:** **Reading B.** Minimax's version-flag (and gpt-6's coverage map) are checkable against two primary pages — [minimax 1][minimax 2] and [minimax 3][minimax 5] — and gpt-6's §3 maps OWASP 2025 headings to its own rule IDs. A rule set anchored on 2021 omits `unsafe-eval` as a CSP blocker, the A03 lifecycle-script/supply-chain controls, and the A10 fail-closed/over-informative-error controls entirely.
- **Why it matters for Phase 1:** Any rule checklist that cites A06:2021 will under-invest in lifecycle-script blocking (A-28/A-29), minimum release age / cooldown, SBOM, and the A10 error-leakage rules. Phase 1 must use the 2025 per-category pages as source of truth.

### D-02 — Does the guardrail set need an AI-specific layer, or do classic web rules suffice?

- **Reading A (muse-spark, gemini-3.8-flash, openai-gpt-6):** Treat guardrails as classic web-app security + git + deploy + privacy. Muse-spark has zero rules on agent identity, model output handling, or MCP tool governance. Gemini hints at AI-specific risks in prose ("AI models regularly write `USING (true)`", "hallucinate non-existent packages") but states no deterministic rule for them. Gpt-6 covers one LLM-flavored rule (SEC-01's LLM output caution) and otherwise stays in classic controls.
- **Reading B (minimax, deepseek):** Treat the **harness itself as an attack surface.** Minimax dedicates 11 rules (A-01…A-10) to agent identity, prompt-injection via untrusted files read by the agent, system prompt as non-boundary, tool allowlists, MCP pinning, LLM output sanitization, least-privilege AI DB identity, token caps/bounded consumption, and PII redaction before model calls — grounded in OWASP LLM Top 10 2026 ([minimax 13][14]), LLM01/02/05/06/07/10 ([minimax 6][7][9][10][11][12]), MCP Top 10 ([minimax 16]), and OWASP DevSecOps agent pages ([minimax 19][20]). Deepseek independently elevates the same thesis ("the obvious way … fails … because a rule that cannot be checked mechanically becomes an opinion") and includes slopsquat/hallucinated-package verification as a deterministically checkable rule.
- **Resolution:** **Reading B, with integration.** For vibe-fence the binding constraint is not the app's bug surface but the agent's — the harness writes the code that the checks inspect. Without least-agency identity (A-04), tool/MCP pinning (A-05), hallucinated-package verification (A-29), LLM-output sanitization (A-06), and agent-config hardening (A-02), a classic checklist can be bypassed by AI-generated code that passes a syntactic scan.
- **Why it matters for Phase 1:** The scaffold must ship an `agent-permissions.json` / `mcp-allowlist.json` pair, a `slopsquat` pre-install gate, and a middleware guard that the model can propose but never make optional. Copying only the classic layer leaves the fence guarding the app while the agent remains the insider.

### D-03 — Should secrets-in-env be `block` on the first commit, or a softer `warn`/`nudge`?

- **Reading A (muse-spark, minimax, deepseek, gpt-6):** `block` — dual-layer (gitleaks pre-commit + server-side push protection), `.gitignore` before first commit, `git ls-files | grep .env` must be empty. Minimax explicitly makes secret-scan a `warn` on first run only until the allowlist exists, then `block`; deepseek makes `.env` + `.gitignore` self-healing blocks inside `fence init`.
- **Reading B (google-gemini-3.8-flash):** SEC-01 `block` for history, but GIT-01 "mandatory `.gitignore` invariants" `block` is stated as "locks against removal" with less enforcement detail; no explicit dual-layer or first-run escalation is described.
- **Resolution:** **Reading A, specifically minimax's two-phase escalation.** A hard `block` on day one with no allowlist path produces the highest false-positive rate in practice (gemini correctly flags this). Minimax's compromise — `warn` until `secret-scan-allowlist.json` exists, `block` thereafter — keeps the gate honest without training the user to bypass it.
- **Why it matters for Phase 1:** A `block` with no suppression is worse than a `warn`, because the first false positive invalidates the whole secrets gate. Phase 1 must ship the allowlist file format, not just the scanner.

### D-04 — Where to draw the severity line on dependency scanning: `critical-only block` vs `high+critical block` vs `warn`?

- **Reading A (deepseek):** `block` on **critical**, `warn` on high — finer graded, with a "never block on judgement call" discipline.
- **Reading B (muse-spark):** `block` for **critical/high** fixable CVEs, `warn` for moderate — cites `npm audit --audit-level=high` as the CI failure point.
- **Reading C (gpt-6):** `block` on **applicable high/critical or malicious packages**, with a documented triage record (reachability evidence, expiring mitigations), and an explicit "unknown ≠ pass" rule requiring mitigation records; forbids `--audit fix --force`.
- **Reading D (minimax):** `warn` that **fails CI at `high`** in practice (`npm audit --audit-level=high`), but the *primary severity token* is `warn` for audit findings, `block` for lockfile/commit drift — deliberately keeping audit findings at `warn` until triage quality improves.
- **Resolution:** **Reading C as policy, B as the default check command.** Gpt-6's position is the only one that handles scannability correctly for beginners: raw `npm audit --audit-level=high` as a blocking check is correct as a *starter* gate (Reading B), but a maturing project must graduate to applicability-checked findings with evidential records — otherwise every transitive CVE becomes a shipped-blocker the user silences globally. Phase 1 therefore ships `npm audit --audit-level=high` as the out-of-box CI failure (Reading B), documented as evolving toward gpt-6's applicability-checked model via a mitigation record, and treats "unknown (scanner failed)" as not passing.
- **Why it matters for Phase 1:** Picking `warn`-all (gemini SEC-07) lets known CVEs ship silently. Picking `block`-everything with no triage path teaches `npm audit --ignore`. The escalation path — `block` by default, mitigatable with evidence + expiry — is the durable design.

### D-05 — Should git style (Conventional Commits, PR hygiene) be enforced, or kept soft?

- **Reading A (muse-spark):** Conventional Commits `warn`, with branch protection on `main` and PR hygiene at `nudge`; but the tone treats commit conventions as near-mandatory ("commitlint + Husky on `commit-msg`").
- **Reading B (gemini):** GIT-04 Conventional Commits as `nudge` (standardized semantic commits), but git hygiene overall is lighter than peers.
- **Reading C (deepseek):** G-04 commits as `warn`; distinguishes "small and single-purpose" commits (checkable via diff size / lockfile+source mixing) from style.
- **Reading D (minimax + gpt-6):** **Contingent nudge** — Conventional Commits is `nudge` for solo dev (1 contributor), `warn` at 2+ contributors, detected mechanically via `git shortlog -sne | wc -l`; the harness writes the message itself so the user is never asked to type one. Gpt-6 explicitly says "do not block a security fix solely because its message lacks a preferred prefix."
- **Resolution:** **Reading D.** Minimax + gpt-6's contingent escalation reconciles the "always enforce" and "never enforce" camps and is the only proposal that is mechanically checkable without user friction. Commit *atomicity* (small, single-purpose) can be `warn` from day one; commit *convention* escalates with team size.
- **Why it matters for Phase 1:** Treating Conventional Commits as a global `block` is the most cited over-blocking anti-pattern (minimax §10) and would make `fence check` hostile to the solo beginner — exactly the user vibe-fence is for.

### D-06 — Should `.env` / env-var handling require just gitignore hygiene, or platform-scoped environment management?

- **Reading A (muse-spark, gemini, minimax):** `.env` hygiene + Vercel Environment Variables scopes (Production / Preview / Development) with separate credential sets; value-equality checks across scopes; Sensitive-type write-only handling. Muse-spark's D-01 packet is the most complete platform description; minimax adds the "Sensitive does not protect the browser bundle" subtlety.
- **Reading B (deepseek):** `.env` hygiene plus minimal `vercel env ls` presence check and `NEXT_PUBLIC_` grep only; less emphasis on cross-environment value divergence or platform-specific scope semantics.
- **Reading C (gpt-6):** `.env` hygiene plus full deployment-aware model: DEP-01's "environment changes apply to new deployments only" (with redeploy requirement), DEP-02's sensitivity-aware handling across preview/prod, and PRV-adjacent secret-in-config checks; ties env handling to git hygiene (GIT-01's staged-content scan) and to the build gate.
- **Resolution:** **Reading A as shipped scaffold, C as the redeploy discipline.** The platform-scoped environment model (A) is correct and is the only one that survives Vercel's actual docs. Gpt-6's contribution — that a config change without a redeploy is a stale deploy — is a `warn`-level teaching check that should accompany it ("this needs a new deploy, not a restart").
- **Why it matters for Phase 1:** A scaffold that gets `.env` gitignore right but creates preview deployments with prod creds ships a live data-exposure. The cross-environment value check is the gate that catches it.

### D-07 — How should severity escalation be modeled: per-rule fixed labels or app-lifecycle stages?

- **Reading A (muse-spark, gemini, deepseek, gpt-6):** Per-rule fixed severity tokens (`block`/`warn`/`nudge`) with some `warn→block at public launch` escalation noted ad hoc (muse-spark D-06 "checklist is `block` for public launch"; gpt-6 `warn`/`block` conditional on applicable data or exposure; deepseek deterministic decision tree).
- **Reading B (minimax):** Severity is a **policy derived from declared app intent** — one question at init (local / shared / public) held in `.fence/app-profile.json`; 14 unconditional `block` rules at local, +15 at shared, +26 at public (55 of 60 `block` at public; 5 `nudge` become `warn`). AI-specific rules (A-01…A-10) are `block` even at "local" because the compromise vector is the agent, not the user.
- **Resolution:** **Reading B as the architecture; Reading A's per-rule severity table as the starting data that feeds it.** Minimax's §9.1 mapping is the only proposal that reconciles "the user should not have to decide on security" with "the user must not be blocked on a weekend prototype." The user decides one fact (intent); the harness derives everything else. Per-rule severities without this framing produce either chronic over-blocking or silent exposure.
- **Why it matters for Phase 1:** Without an app-profile severity policy, `fence check` has a single fixed gate and must choose between blocking prototypes and allowing launches to be insecure. The profile is vibe-fence's genuine contribution over a generic linter.

## 4. Gaps in the collective research

What NOBODY found. These become the next research batch, or explicit Phase 1 risks.

1. **File upload safety (MIME + extension + size + storage ACL + malware scanning).** Every contributor flags this as a gap and stops — muse-spark gap 2, minimax §12 gap 3, deepseek omits it, gemini omits it, gpt-6 covers it at SEC-16 but the collective lacks a hardened enforcement packet (allowlisted storage helpers + virus scan adapter + storage ACL checks). *Close with:* dedicated follow-on batch on upload helpers (MIME sniffing vs header, polyglot/RCE vectors, object-storage ACLs, ClamAV provider integration); wire as `block` for upload features.
2. **Outbound request / SSRF allowlisting for user-supplied URLs.** A common AI-generated feature ("fetch this URL and show a preview") has no allowlisted wrapper in any contributor. OWASP A01:2025 now folds SSRF into access control, but no contributor ships a deterministic fetch wrapper. Muse-spark gap 4, minimax §12 gap 4, deepseek S-14 notes `allowlist helper` but doesn't define one. *Close with:* `safeFetch()` wrapper spec (scheme/IPv4/IPv6/port allowlist, private/loopback denial, redirect-hop validation, egress controls) + Semgrep rule covering `fetch(req.*url)`.
3. **Non-Vercel deploy targets and framework-divergence detection.** Rules are Next.js/Vercel-shaped; Vite→`VITE_`, Astro→`PUBLIC_`, Remix, SvelteKit, Netlify/Fly/Railway/Cloudflare Pages, and self-hosted VPS are unscoped. Minimax notes framework detection as needed work; gpt-6 flags plan/scope availability dependence. *Close with:* framework-detection step + adapter layer for env-prefix and deploy-check semantics.
4. **Measured false-positive / false-negative rates on agent-written code.** No contributor has data on how any check (gitleaks, npm audit, CSRF/CSP linters) behaves on the actual population that matters — agent-generated code — vs the human code those tools were tuned on. Deepseek gap 6, minimax gap reasoning, gpt-6 gap 1 all call this out. *Close with:* build a corpus of agent-generated fixtures (with the adversarial suite in implication 12) and measure before claiming coverage.
5. **Quantified approval-fatigue / guardrail-fatigue budget on the fence itself.** Minimax §10 + deepseek §6 warn that a `block` the user learns to ignore is net negative, but nobody measures how many prompts or blocks a non-technical user tolerates before disabling the harness. Deepseek ties it to stream 05's gate budget (U-02); minimax ties it to §10 patterns; gpt-6 implication 14 proposes turbo/teaching-level independence as untested design. *Close with:* evaluation study on "blocks per session before disable" vs trust, varying `warn→block` thresholds.
6. **Jurisdiction-complete privacy beyond EU/UK/Canada generalities.** All four strong privacy treatments use GDPR/EDPB/ICO/Canadian PIPEDA; none covers California CCPA/CPRA operational detail, COPPA/children's data, payment-card PCI scope, or health/financial sector overlays. Gpt-6 PRV-08 + minimax A-55 gaps call this out. *Close with:* add explicit jurisdiction profiles only when those data categories appear in inventory; treat the privacy rules as EU/UK-shaped defaults with jurisdiction-gating.
7. **PII-in-LLM-prompt boundary as a concrete deployable control.** Muse-spark gap 5 ("PII detection in LLM prompts") and minimax A-09's redaction helper describe the risk but the collective lacks a production-ready redaction policy (what to redact, what to leave, how to audit it, jurisdiction interaction with Stream 06 model integration). *Close with:* specify `src/server/llm/redact.ts` redaction categories + logging contract + consent interaction, in joint follow-on with Stream 06.
8. **Rate-limiting / abuse / cost-ceiling policy for auth and paid services.** Muse-spark gap 3, gpt-6 SEC-17, and minimax A-26/A-08 name it; no contributor ships a concrete enforcement spec (shared atomic counters, per-route thresholds, retry/timeout shapes, cost ceilings). *Close with:* rate-limit spec keyed to inventory auth/payment routes, with platform WAF fallback (Vercel WAF rate limiting) as outer bound.

## 5. The consolidated answer

Five independent researchers agree that vibe-fence must enforce a non-negotiable floor of engineering hygiene — secrets, injection, headers, auth, supply-chain, git, deploy, and privacy — and that every enforcement must be a command that returns a verdict (`proven` at OWASP/Vercel/MDN/ICO/EDPB source depth), not prose advice. The 2025 OWASP web and 2026 GenAI LLM category sets (not 2021) are the right frame, because they added the supply-chain and mishandling-of-exceptions categories that matter most to agent-generated code. What the classic checklist alone misses is equally settled across the two AI-specific contributors: the **agent harness itself is the attack surface** — least-agency identity, tool/MCP pinning, hallucinated-package verification, LLM output sanitization, and redaction before model egress are guardrails, not features. Severity is not a fixed label but a **policy derived from one user-declared fact** (local / shared / public), with the AI-specific rules as `block` even at local. A guardrail the user can silently turn off, or that fires on public keys and asset hashes, is not a guardrail — it is the over-blocking failure mode the fence must not become. Ship deterministic checks in the scaffold, keep gates outside the agent's write scope, and let the model explain while the checker decides.

### Avoid (do not do this)

1. **"Be careful with secrets / SQL / XSS" as a guardrail** (all 5; sharpest framing deepseek §1 + minimax A-13) — Without a command that returns a verdict, it's a nudge mislabelled as a gate and trains approval fatigue; the fence must fail on the check result, not the prose.
2. **Letting the agent edit or relax its own checks** (minimax A-02/A-50 + gpt-6 implication 4 + deepseek G-06/G-07) — Checks live in `tools/` (agent write-scope denied), hooks install from a pinned source, CI gate is server-side; workflow/test-exclusion/ignore-list/deployment-check edits are policy changes requiring independent authorization; all release paths including manual CLI are gated.
3. **Blocking the user on Conventional Commits / PR mandates / file-size ceilings in solo hobby mode** (minimax §10 + gpt-6 implication 8 + deepseek contingent escalation) — Solo: PR is `nudge`, Conventional Commits is `nudge` (the harness writes the message), file-size ceiling is `nudge`; escalation to `warn` only at 2+ contributors. These are the canonical over-blocking patterns.
4. **Shipping CSP `block` / secret-scan `block` without a suppression allowlist** (minimax §10 + gemini gap + gpt-6 mitigation expiry) — CSP ships Report-Only first; secrets lint ships `warn` until `secret-scan-allowlist.json` exists; every `block` must have a documented suppression path with a reason string.
5. **Treating preview deployments / `hard-to-guess URLs` as access control, or treating preview-isolated state as production-safe** (gpt-6 DEP-02 + minimax A-45) — Preview URLs are URLs, not ACLs; preview code with prod creds can mutate live data; require distinct credential scopes + Deployment Protection + value divergence checks.
6. **Conflating CI "green" on stale/skipped/missing checks with proof that this revision passed** (gpt-6 GIT-03 + minimax A-39 + Vercel Deployment Checks "skipped when script absent" trap) — Gpt-6's "final policy job that checks expected jobs actually ran" is the fix; include a harmless failing fixture to prove promotion would be blocked.
7. **Deleting or skipping tests to make the gate pass (deepseek H-06) or catching authorization failures and continuing with default success (gpt-6 SEC-19)** — Both are `block`-level attacks on the fence's own evidence chain; diff-lint for `.skip`/`.only` / assertion-removal alongside failing runs; auth exceptions must fail closed.
8. **Running dependency installs with arbitrary `postinstall` by default** (minimax A-28 + gpt-6 HYG-04 + deepseek S-05) — Default to `npm ci --ignore-scripts` / `pnpm.onlyBuiltDependencies: []`; explicitly allowlist packages that need scripts with a recorded justification.
9. **Collecting data/cookies first and gating later, or calling a banner a privacy program** (gpt-6 PRV-07 + minimax A-57 + muse-spark P-05) — A banner that loads trackers first does not enforce consent; inventory tags/storage/network and test fresh/rejected/accepted/withdrawn states.
10. **Letting the companion LLM decide `block` outcomes** (minimax §9 determinism law + gpt-6 implication 11) — The model explains and repairs; deterministic policy, host integrations, and tests decide pass/fail. An LLM's "looks safe" is not a verified signature, authorization check, or test execution.

### Invent (we must build this, nobody has)

1. **App-profile severity escalation (minimax §9.1)** — One question at `fence init` (`local` / `shared` / `public` in `.fence/app-profile.json`) derives every rule's severity: 14 unconditional `block` at `local` (AI-specific + `NEXT_PUBLIC_` + lifecycle + lockfile), +15 at `shared`, +26 at `public`; 5 `nudge` remain `warn` even at `public`. No other harness has a policy keyed to declared intent rather than a fixed label.
2. **`NEXT_PUBLIC_` / `VITE_` / `PUBLIC_` secret-shape lint** (minimax A-42 · deepseek S-03) — No standard linter does this; vibe-fence-specific rule matching value pattern + name pattern with framework detection; `warn` until allowlist, then `block`.
3. **Slopsquat / hallucinated-package pre-install gate** (minimax A-29) — Resolve against registry; assert existence + expected owner/description + age ≥ cooldown + lockfile presence; refuse names absent from registry — the only deterministic defence against LLM-invented package names.
4. **Deterministic `block` function with `unknown` ≠ pass semantics** (deepseek decision tree + gpt-6 four-outcome + muse-spark P0 table + minimax determinism split) — Encodes severity algorithmically so new rules cannot be assigned severity by vibes; single allowlist schema (`secret-scan-allowlist.json`, `csrf-exempt.json`, `dependency-policy.json` with reason strings) governs all suppressions.
5. **Self-hardened guardrail boundary** (gpt-6 GIT-05/GIT-03/DEP-04 + minimax A-05/A-04 + deepseek G-06/G-07) — Guardrail policy + CI + deploy gates live outside the agent's write scope; edits to workflows / `.gitignore` / `pre-commit` / deployment-check config are policy changes requiring separate authorization; all release paths verified.
6. **Agent-identity and harness-surface hardening** (minimax A-02/A-04/A-05/A-50/A-54) — Per-task scoped short-lived tokens (not developer creds), deny-by-default permission allowlist in `agent-permissions.json`, MCP allowlist with OPA deny on `@latest`, `AGENTS.md` under CODEOWNERS + invisible-Unicode scan, untrusted fetched content in `<untrusted-content>` envelopes, `tools/` excluded from agent edits.
7. **Adversarial fixture suite that tests the fence itself** (gpt-6 implication 12 + implication 6 queue record shape) — Seeded fake secrets, missing CI scripts, skipped jobs, disabled checks, wrong-env identifiers, cross-user requests, reflected origins, replayed webhooks, public private-data caches, pre-consent trackers — plus valid cases to measure false blocks; queue entries carry `merge` / `deploy` / `accepted-behavior` as distinct states.
8. **Teaching + turbo decoupled from the safety gate** (gpt-6 implication 14 + muse-spark "invent the escalation" + deepseek "never block on a judgement rule") — Teaching-level `max/med/min/silent` reuses the one-sentence teach text at varying verbosity with detailed evidence on demand; turbo may remediate routine queued items inside agreed scope but never disables secret scanning, expands DB authority, skips release checks, or activates unknown tracking.

## 7. Open questions we could not resolve

- [ ] **Is the app-profile three-tier the right partition, and where exactly does `shared → public` trigger?** Minimax proposes three tiers at `fence init`; gpt-6's "intent" is similar but doesn't specify re-declaration. An evaluation should measure prototype friction vs launch risk at two vs three tiers. — Experiment: ship both in A/B and measure blocks-per-session-before-disable vs post-launch incident rate.
- [ ] **Should high-severity audit findings be `block` or `warn` out of the box?** B (`block` at `audit-level=high`) vs D (`warn` with mitigation) — see D-04. The right answer depends on reachability of transitive findings. — Experiment: on a corpus of vibe-coded repos, compare raw `npm audit high` block rate vs reachability-checked findings vs manually triaged findings.
- [ ] **What is the false-positive calibration for the `NEXT_PUBLIC_` shape matcher, and when does an allowlist actually become a `block`?** All five flag the public-key / asset-hash problem (gemini gap + minimax §10 pattern 2) but none measures it. — Experiment: run the matcher on a corpus of real Next.js repos; tune prefix+entropy threshold until PPV is acceptable; define promotion criterion from PPV, not time.
- [ ] **Do non-technical users tolerate the `check → fix → re-check` loop, or does it produce the fatigue it aims to prevent?** Deepseek's severity procedure and minimax's §10 predict fatigue at scale; no contributor measured it. — Experiment: instrument blocks/warns/nudges per session per rule (muse-spark implication 12) and track disable rate vs teaching-level and `warn→block` timing.
- [ ] **Does code-gated-on-tests actually beat code-repaired-by-Agentless on agent-written code?** Minimax's audit of prior stream-03 numbers (§10) invalidates prior siblings' reflexion/self-refine deltas; the fence's code-formation (Agentless vs guard-rail) design is unresolved. — Experiment: head-to-head on a private eval set with cost-of-pass reporting (minimax implication 12).
